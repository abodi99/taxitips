# TaxiTips — Status Report

Generated by an inspection pass over the actual repo contents (`taxitips-api`, `taxitips-app`, `taxitips-web`), the live migration files, and the Flutter client. Nothing here is assumed from the briefing — everything below was verified by reading code.

Note on naming: the briefing refers to `/api`, `/app`, `/web`. The actual repo uses `taxitips-api`, `taxitips-app`, `taxitips-web`. This doc uses the real names.

---

## 1. Confirmed current behavior

**Backend**: self-hosted Supabase (Postgres/Auth/PostgREST) on Coolify, service `supabase-taxitips`. Schema covers profiles, companies, company_members (roles: company_owner/company_admin/driver), billing_accounts, subscriptions, devices (driver units, joined via company `join_code`), device_transfer_codes, tickets, app_config, and `alerts` (the disturbance/opportunity table).

**Worker** (`taxitips-api/worker`): a single long-running Node/Express process that:
- Polls Trafiklab (GTFS-RT service alerts, Skåne + neighboring regions) and Trafikverket (road situations) on a fixed interval (`POLL_INTERVAL_MS`, default 60s).
- Scores every alert with a hand-tuned regex/keyword ruleset ([taxiRelevance.js](taxitips-api/worker/src/taxiRelevance.js)) — Swedish-language pattern matching for "serious" vs "medium" vs "ignore", hub-name detection, Skåne-geofencing.
- Computes an H3 index (`h3-js`, resolution 8) and a `demand_score` (0–100) via `calculateDemandSignal`, including a "Last Train Risk" boost for late-night train disruptions.
- Upserts directly into `public.alerts` — raw source data and derived score live in the **same row, same table**.
- Also hosts the Stripe webhook endpoint (`POST /webhooks/stripe`) with idempotency via `processed_webhook_events`.

**Client read path**: Flutter app calls `get_smart_alerts(lat, lon)`, a `SECURITY DEFINER` RPC that computes Haversine distance and a `worth_it_score` (`demand_score - distance_km*2`, zeroed if time-to-expiry is tighter than distance+10 min) directly in SQL, then returns JSON.

**Billing**: company-level Stripe subscription. Signup flow ([signup, in api_client.dart](taxitips-app/lib/api_client.dart:240)) creates a company + `company_owner` membership, then immediately calls `createCheckoutSession`. Stripe webhook updates `companies.status` and upserts into `subscriptions` on any `customer.subscription.*` event.

**Push**: FCM token registration exists client-side ([push_service.dart](taxitips-app/lib/push_service.dart)) and tokens are stored on `devices.push_token`. That's it — see gap below.

**Web** (`taxitips-web`): this is **not** just marketing pages as the briefing assumed. It includes `admin.html`/`admin.js`, `dashboard.html`/`dashboard.js`, `portal.css` — a real company/admin portal alongside the marketing site (`index.html`, `pricing.html`, `join.html`). Worth re-scoping the briefing's "web = marketing only" assumption.

## 3. Security gaps (P0-relevant)

1. **`alerts` table is publicly readable with no gate.** RLS policy: `alerts_select_authenticated ... for select using (true)` ([rls.sql:70-71](taxitips-api/supabase/migrations/20260823000002_rls.sql:70)) — the comment even says "public read for driver apps using anon + RPC" as if this were an intentional MVP shortcut, not the final state. Since `alerts` now carries `demand_score`, `h3_index`, and `reasons` (added in the smart_signals migration), this table **is** the premium "opportunities" data the briefing explicitly says must never be public.
2. **`get_smart_alerts` RPC has zero entitlement/auth check.** It's `SECURITY DEFINER`, callable by anyone with the anon key (which is compiled into every client), and returns full scored results with no company/subscription check inside the function body at all ([rpc_worth_it.sql](taxitips-api/supabase/migrations/20260829000002_rpc_worth_it.sql)).
3. **No `entitlements` concept exists in Postgres at all** — no function, no view, nothing. The briefing's required model (`entitlements()` as canonical server-side truth) has to be built from scratch, not fixed.
4. **`alert_feedback.alert_id` is `uuid` but `alerts.id` is `text`.** This FK is a type mismatch — it cannot have been successfully applied against a database where `alerts` already existed with `text` ids, or it was applied against an empty/different environment. Either way, `submitAlertFeedback` in the Flutter client ([api_client.dart:641](taxitips-app/lib/api_client.dart:641)) passes a `text`-shaped id and will fail against a correctly-typed column, or the constraint was never actually enforced. Needs to be fixed as part of the P0 schema pass, not deferred.
5. **DB credentials**: `.env.example` shows the worker using `SUPABASE_SERVICE_ROLE_KEY` (full bypass-RLS access) for all of its writes, including the join/scoring pipeline. The briefing requires a least-privilege role split between migrations and runtime writes — currently there is only ever one role in use (service_role) for the worker's entire write path.
6. **No automated backup evidence found** — no backup scripts, no S3/Coolify backup config in the repo. Should be treated as not yet implemented, matching the briefing's P0 item.

## 4. Billing sync state

- Idempotency is handled correctly at the webhook layer via `processed_webhook_events` (insert-then-check pattern, [index.js:45-54](taxitips-api/worker/src/index.js:45)).
- Only events prefixed `customer.subscription.` are handled. `checkout.session.completed` (needed to capture `stripe_customer_id` on first purchase if not already linked) and `invoice.payment_failed` (needed for dunning/grace period — note `subscriptions.grace_until` exists in the schema but nothing appears to set it) are not handled.
- Sync failures are logged to `processed_webhook_events.error` but nothing reads that column back out — no alerting, no retry job. This half-satisfies the briefing's "no silent sync failures" rule (visible in DB) but doesn't fulfill "retryable."
- The duplicate edge-function handler (see above) is the single biggest billing risk right now — it's a live foot-gun if Stripe's webhook URL ever points there.

## 5. Data-ingestion state

- Trafiklab + Trafikverket pollers both have working mock-mode fallbacks (`TRAFIKLAB_API_KEY=mock`, `TRAFIKVERKET_MOCK=1`), which is good for local dev.
- Scoring logic (`taxiRelevance.js`) is a substantial, carefully-tuned Swedish regex ruleset — this is real product logic, not a stub, but it's centralized in one file with hardcoded thresholds (not the "centrally configured" externalized rule model the briefing asks for; "centrally configured" here just means "one file," not database-driven or hot-reloadable).
- **`source_events` vs `opportunities` separation does not exist.** Raw polled data and the derived score are merged into one `alerts` row at ingestion time ([poller.js:mapAlert](taxitips-api/worker/src/poller.js:20)). This is the core P1 architectural item and is a genuine rework, not a rename.
- SMHI is not integrated at all yet (correctly deferred to P2 per the briefing).
- Confidence/explainability: `reasons text[]` exists and is populated, so the "which source_events, which rule, what confidence" requirement is partially met for the *rule name*, but there's no link from an `alerts` row back to which raw poll/API response produced it (no raw-event table, no foreign key) — can't reconstruct provenance after the fact.

## 6. Push pipeline state

Registration-only. Token capture, storage, and refresh work. There is no code path anywhere in the worker, an edge function, or a cron job that reads newly-scored high-value alerts and calls FCM's send API. This is 100% greenfield work, not a bug fix.

## 7. Proposed order of fixes (against the P0/P1 list)

**P0 — do these first, in this order:**
1. Fix the `alerts.id` / `alert_feedback.alert_id` type mismatch (blocks everything else touching that table cleanly).
2. Split `alerts` conceptually enough to add a real entitlement gate *without* waiting for the full `source_events`/`opportunities` rework — i.e., lock down RLS + rewrite `get_smart_alerts` to check company entitlement before returning scored rows. This is the single highest-leverage fix: it closes the "premium data is public" hole immediately.
3. Build `entitlements()` as a real Postgres function (company status + subscription state → boolean/tier), wire it into `get_smart_alerts`, and have the Flutter client actually call and respect it (currently calls nothing).
4. Resolve the duplicate Stripe webhook handlers down to one canonical path; add `checkout.session.completed` and `invoice.payment_failed` handling.
5. Create a scoped least-privilege Postgres role for the worker's runtime writes, separate from whatever role runs migrations.
6. Stand up automated Postgres backups (pg_dump → S3-compatible storage on Coolify) with a verified test restore.
7. Build the actual push-send path (worker or new edge function reads newly high-scored alerts → FCM), with dedup and expiry.
8. Regenerate `ALL_MIGRATIONS.sql` so the documented Studio-paste path isn't silently stale, or deprecate that doc path in favor of the CLI-only flow if that's the actual deployment method now.

**P1 — after P0 lands:**
9. Do the real `source_events` → `opportunities` split (this is a schema migration + worker rewrite, expand/migrate/contract per the briefing's rule).
10. GTFS static context + Next Departure.
11. Last Departure Risk + Transport Gap (some of this logic already exists ad hoc inside `calculateDemandSignal`'s "Last Train Risk" — formalize it as its own rule under the new model).
12. Stranded Score v1, Personal Worth-It v1 (partially exists as `worth_it_score` in the RPC — needs to move from ad-hoc SQL expression to the centrally-configured rule engine), driver action cards.
13. 🚕/👍/👎 feedback capture (schema exists as `alert_feedback`, blocked on item 1 above).

**P2**: as specified in the briefing, no changes.
